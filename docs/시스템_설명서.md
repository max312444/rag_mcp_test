# Agentic RAG + MCP 시스템 설명서

## 1. 프로젝트 개요

### 1.1 무엇을 하는 시스템인가?

PDF 문서(영진전문대학교 학칙)를 AI가 이해할 수 있는 형태로 가공하여,
Claude Desktop에서 자연어로 질문하면 문서 내용을 기반으로 정확한 답변을 제공하는 시스템.

**핵심 키워드**: Agentic RAG, MCP(Model Context Protocol), Hybrid Search, Cross-Encoder Reranking

### 1.2 기존 RAG vs Agentic RAG

```
[기존 RAG - Naive RAG]
사용자 질문 → 벡터 검색 1회 → 결과 반환 → LLM 답변
                (끝. 결과가 나쁘든 좋든 1번만 검색)

[Agentic RAG - 이 프로젝트]
사용자 질문 → LLM이 판단 → 도구1 호출 → 결과 확인
                          → 결과 부족? → 도구2 호출 → 재확인
                          → 표 필요? → 도구3 호출 → 종합 답변
                (LLM이 스스로 어떤 도구를 쓸지, 몇 번 쓸지 결정)
```

**Agentic의 핵심**: LLM(Claude)이 단순 소비자가 아니라 **오케스트레이터(지휘자)** 역할.
6개 도구 중 상황에 맞는 것을 선택하고, 결과가 불만족스러우면 다른 전략으로 재시도한다.

### 1.3 전체 아키텍처

```
┌─────────────────────────────────────────────────────────┐
│                    Claude Desktop                        │
│   사용자 질문 → Claude가 도구 선택 → 답변 생성           │

              │ MCP (stdio)                   │

│                                                          │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────┐ │
```

## 2. 데이터 파이프라인 (loader/)

PDF → 텍스트/표 추출 → 섹션 분리 → 청킹 → 임베딩 → DB 저장

### 2.1 extract.py - PDF 추출

**역할**: PDF에서 텍스트와 표를 추출

```python
# 3개 함수

extract_text_by_page(pdf_path)
# pdfplumber로 페이지별 텍스트 추출
# 표가 있으면 마크다운으로 변환해서 텍스트에 합침
# 반환: [{"page_num": 1, "text": "..."}, ...]

extract_sections(pages)
# 전체 텍스트를 "제X장" 패턴으로 섹션 분리
# 정규식: r'^(제\d+장\s+[^\n<]+)' (줄 시작의 "제N장 제목")
# 반환: [{"section": "제1장 총칙", "content": "...", "page_num": 1}, ...]

extract_tables_structured(pdf_path, sections)
# 표를 별도로 구조화 추출
# 각 표에 소속 섹션, 캡션, 헤더, 행 데이터 포함
# 반환: [{"page_num": 7, "section": "제6장", "headers": "[...]",
#         "content_markdown": "| ... |", "rows": [...]}, ...]
```

**표 처리 방식**:
- `pdfplumber.page.extract_tables()` → 2차원 리스트로 추출
- `table_to_markdown()` → 마크다운 테이블 문법으로 변환
- 텍스트 본문에도 포함 + `doc_tables` 테이블에 별도 저장 (이중 저장)
- 이중 저장 이유: 벡터 검색으로도 찾고, `get_table` 도구로 구조적 접근도 가능하게

### 2.2 chunker.py - 청킹 (Overlap 방식)

**역할**: 섹션을 검색 가능한 작은 단위(chunk)로 분할

```
[청킹 전략: 3단계]

1단계: 의미 단위 분리
  "제X장" (Parent) → "제X조" (Child) 단위로 분리
  정규식: r'(?=제\d+조(?:의\d+)?\s*[\(（])'

2단계: Overlap 적용
  각 Child에 이전 조의 끝 150자 + 다음 조의 앞 150자를 포함
  → 조 경계에서 정보 손실 방지

  예시:
  ┌─────────────────────────────────┐
  │ [이전 조 끝 150자] ← overlap   │
  │                                 │
  │ 제3조(위치) ← 본문             │
  │ ① 본 대학의 복현캠퍼스는...    │
  │                                 │
  │ 제4조(설치 계열...) → overlap  │
  │ [다음 조 앞 150자]             │
  └─────────────────────────────────┘

3단계: 긴 조는 Sliding Window 추가 분할
  chunk_size(800자) × 1.5 초과 시 → 800자 단위로 분할 (150자 overlap)
```

**왜 이 방식인가?**

| 방식 | 장점 | 단점 |
|------|------|------|
| 고정 크기 분할 | 균일한 청크 | 의미 단위가 깨짐 |
| 의미 단위 분할 (조 기준) | 의미 보존 | 경계에서 정보 손실 |
| **의미 단위 + Overlap (현재)** | **의미 보존 + 경계 정보 유지** | 약간의 중복 |

### 2.3 embed_load.py - 임베딩 & DB 로딩

**역할**: 청크를 벡터로 변환하고 DB에 저장

```
처리 흐름:
PDF 추출 → 섹션 분리 → 표 추출 → 청킹
→ 문서 등록 (documents 테이블)
→ Parent 삽입 (parent_chunks - 장 전체 내용)
→ Child 임베딩 생성 + 삽입 (child_chunks - 조 단위, 벡터 포함)
→ 표 임베딩 생성 + 삽입 (doc_tables - 마크다운 + JSON + 벡터)
```

**임베딩 모델**: `jhgan/ko-sroberta-multitask`
- 한국어 특화 Sentence-BERT
- 768차원 벡터 생성
- 문장/문단의 의미를 숫자 벡터로 변환
- "졸업 학점"과 "수료에 필요한 학점 수"가 비슷한 벡터를 가지게 됨

**DB 스키마**:

```sql
documents        -- 문서 레지스트리 (멀티 문서 지원 가능)
├── parent_chunks  -- 장(Chapter) 전체 내용 (25개)
│   └── child_chunks  -- 조(Article) 단위 + 임베딩 벡터 (303개)
└── doc_tables     -- 구조화된 표 데이터 + 임베딩 벡터 (31개)
```

## 3. MCP 서버 (mcp_server/)

### 3.1 server.py - 6개 Agentic 도구

Claude Desktop과 stdio(표준입출력)로 통신하는 MCP 서버.
FastMCP 프레임워크 사용.

#### 도구 1: search_docs (의미 기반 검색)

```
질문 → Bi-Encoder로 임베딩 → pgvector 코사인 유사도 검색 (top 20)
     → Cross-Encoder Reranking (top 5) → 품질 평가 → 결과 반환

사용 시점: 자연어 질문 ("휴학 조건이 뭐야?")
```

**검색 과정**:
1. 질문을 ko-sroberta로 768차원 벡터로 변환
2. DB의 모든 child_chunks 벡터와 코사인 유사도 계산
3. 상위 20개 후보를 Cross-Encoder(ko-reranker)로 재순위화
4. 최종 상위 5개 반환

#### 도구 2: search_keyword (키워드 검색)

```
질문 → pg_trgm trigram 유사도 + ILIKE 매칭 → 결과 반환

사용 시점: 정확한 용어 ("제32조", "NCS", "74학점")
```

**왜 필요한가**: 벡터 검색은 의미는 잘 잡지만, 숫자나 고유명사는 못 찾을 수 있음.
"제32조"라는 정확한 키워드는 키워드 검색이 훨씬 정확.

#### 도구 3: search_hybrid (하이브리드 검색)

```
질문 → 벡터 검색 (top 20) + 키워드 검색 (top 20)
     → RRF (Reciprocal Rank Fusion)로 결합
     → Cross-Encoder Reranking (top 5) → 결과 반환

사용 시점: 복잡한 질문 ("2년제와 3년제 졸업학점 차이")
```

**RRF 공식**:
```
rrf_score(d) = Σ (weight / (k + rank(d)))

- k = 60 (표준 상수)
- weight: semantic 0.7, keyword 0.3 (기본값)
- 두 검색에서 모두 상위인 문서가 높은 점수
```

#### 도구 4: list_sections (목차 조회)

```
DB에서 parent_chunks의 섹션명, 페이지, 길이 조회 → 목록 반환

사용 시점: "이 문서에 뭐가 있어?", 검색 전 구조 파악
```

#### 도구 5: get_section (섹션 전문 조회)

```
섹션명으로 parent_chunks 검색 (ILIKE 부분 일치) → 전체 내용 반환

사용 시점: "제7장 전체 내용 보여줘"
```

#### 도구 6: get_table (표 조회)

```
table_id 지정 → 해당 표 마크다운 반환
table_id 없음 → 전체 표 목록 반환
section_filter → 특정 섹션의 표만 반환

사용 시점: "졸업학점 기준표 보여줘", "학과 목록 알려줘"
```

### 3.2 reranker.py - Cross-Encoder Reranking

**Bi-Encoder vs Cross-Encoder**:

```
[Bi-Encoder (1단계 검색 - ko-sroberta)]
질문 → 벡터A    문서 → 벡터B    코사인유사도(A, B)
  (질문과 문서를 독립적으로 인코딩 → 빠름, 하지만 정밀도 낮음)

[Cross-Encoder (2단계 Reranking - ko-reranker)]  
(질문 + 문서) → 하나로 합쳐서 인코딩 → 점수
  (질문과 문서를 함께 고려 → 느림, 하지만 정밀도 높음)
```

**왜 2단계인가?**
- Cross-Encoder는 정확하지만 모든 문서에 적용하면 너무 느림 (303개 × 수초)
- Bi-Encoder로 빠르게 20개 후보 추림 → Cross-Encoder로 20개만 정밀 순위화
- 이것이 **단일 패스 Reranking** (후보 20개 → 최종 5개)

**왜 2단계(더블) Reranking은 안 했나?**
- 전체 청크가 ~303개로 소규모
- 단일 패스로도 충분한 정밀도
- 2단계 Reranking은 수만 개 이상 청크가 있는 대규모 시스템에서 의미 있음

### 3.3 검색 실패 처리

```python
SIMILARITY_THRESHOLD = 0.4

# 유사도 기반 품질 평가
≥ 0.6  → [검색 품질: 높음]
≥ 0.4  → [검색 품질: 보통]
< 0.4  → [검색 품질: 낮음] + "다른 도구 사용 제안 메시지"

# 결과 0건
→ "관련 내용을 찾을 수 없습니다" + 대안 도구 3가지 제안
```

**Agentic 실패 처리의 핵심**: 도구가 직접 실패를 알려주면, Claude가 이를 읽고
다른 전략(다른 검색어, 다른 도구)으로 **자율적으로 재시도**한다.

## 4. 기술 스택 정리

| 구성요소 | 기술 | 역할 |
|---------|------|------|
| PDF 추출 | pdfplumber | 텍스트/표 추출 |

| 오케스트레이션 | Docker Compose | PostgreSQL + Loader + MCP 서버 |

### 5.2 질문 응답 시 (매 질문마다)

```
사용자: "2년제 졸업학점이 몇 학점이야?"
        │
        ▼
   Claude Desktop (LLM)
   "졸업학점을 물어보고 있고, 표 데이터일 가능성이 높다"
   → search_docs("졸업학점 기준") 호출
        │
        ▼
   MCP Server: search_docs()
   1. "졸업학점 기준" → ko-sroberta → 768차원 벡터
   2. pgvector: 303개 child_chunks와 코사인 유사도 → 상위 20개
   3. ko-reranker: 20개를 Cross-Encoder로 재순위 → 상위 5개
   4. 품질 평가: 최고 유사도 0.35 → [검색 품질: 낮음] 경고
        │
        ▼
   Claude: "결과가 부족하다. 표에 있을 수 있으니 get_table 사용"
   → get_table(section_filter="제7장") 호출
        │
        ▼
   MCP Server: get_table()
   → doc_tables에서 "제7장" 표 반환 (졸업학점 기준표)
        │
        ▼
   Claude: 표 데이터를 읽고 최종 답변 생성
   "2년제 졸업학점은 74학점, 3년제는 110학점입니다."
```

## 6. 대안 기술 및 개선 방향

### 6.1 청킹 전략 비교

| 전략 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **Fixed-size** | 고정 글자수로 분할 | 구현 간단 | 의미 단위 깨짐 |
| **Recursive** | 구분자 우선순위로 재귀 분할 (LangChain 기본) | 범용적 | 문서 구조 무시 |
| **Semantic** | 임베딩 유사도 변화점에서 분할 | 의미 경계 자동 감지 | 계산 비용 높음 |
| **Agentic (Late Chunking)** | 전체 문서 임베딩 후 분할 | 전체 문맥 반영 | 긴 컨텍스트 모델 필요 |
| **의미 단위 + Overlap (현재)** | 조 단위 분리 + 앞뒤 150자 중복 | 법률 문서에 최적 | 문서 구조 의존적 |

**현재 선택 이유**: 학칙은 "제X조"라는 명확한 의미 단위가 있어서 이를 활용하는 것이 가장 정확.
범용 문서라면 Recursive나 Semantic 청킹이 더 적합.

### 6.2 검색 전략 비교

| 전략 | 설명 | 우리 시스템 |
|------|------|------------|
| **Dense Retrieval** | 벡터 유사도 검색 | search_docs |
| **Sparse Retrieval (BM25)** | TF-IDF 기반 키워드 검색 | search_keyword (pg_trgm으로 대체) |
| **Hybrid (RRF)** | Dense + Sparse 결합 | search_hybrid |
| **HyDE** | 가상 답변 생성 후 그걸로 검색 | 미구현 (아래 설명) |
| **Multi-Query** | 질문을 여러 변형으로 바꿔 검색 | 미구현 (아래 설명) |
| **Self-RAG** | LLM이 검색 필요성을 스스로 판단 | Agentic 구조로 부분 구현 |

### 6.3 더 나아갈 수 있는 방향

#### HyDE (Hypothetical Document Embeddings)
```
기존:  질문 → 임베딩 → 검색
HyDE:  질문 → LLM이 가상 답변 생성 → 가상 답변 임베딩 → 검색

장점: 질문과 문서의 임베딩 공간 차이(gap) 해소
단점: LLM API 호출 비용 추가
```

#### Multi-Query Retrieval
```
기존:  "졸업학점?" → 검색 1회
Multi: "졸업학점?" → LLM이 변형 질문 3개 생성:
       - "수료에 필요한 학점 수는?"
       - "졸업 요건 학점 기준은?"
       - "학위 취득 최소 학점은?"
       → 3번 검색 → 결과 합산

장점: 다양한 표현으로 검색해서 recall 향상
단점: 검색 횟수 증가 → 속도 저하
```

#### Graph RAG
```
문서를 지식 그래프로 변환:
"제15조(입학허가)" → 참조 → "제4조(입학정원)"
                  → 관련 → "제16조(편입학)"

장점: 조항 간 관계를 활용한 검색
단점: 그래프 구축 복잡, 소규모 문서에는 과함
```

#### Corrective RAG (CRAG)
```
검색 → 품질 평가 → 결과 좋음? → 사용
                 → 결과 나쁨? → 웹 검색으로 보충 or 질문 재구성

우리 시스템은 품질 평가 + Agentic 재시도로 부분 구현.
웹 검색 보충은 미구현.
```

### 6.4 Reranking 전략 비교

| 전략 | 설명 | 적합한 상황 |
|------|------|------------|
| **None** | Bi-Encoder 유사도만 사용 | 속도 최우선, 소규모 |
| **단일 패스 (현재)** | 후보 20 → Rerank → top 5 | 중소규모 (수백~수천 청크) |
| **2단계 (Cascade)** | 후보 100 → 경량 Rerank → 20 → 정밀 Rerank → 5 | 대규모 (수만 청크 이상) |
| **Listwise Reranking** | 후보 전체를 한번에 순위화 (LLM 기반) | LLM API 사용 가능 시 |

**현재 단일 패스를 선택한 이유**:
- 전체 청크 303개 → 20개 후보면 충분한 커버리지
- Cross-Encoder 20개 처리 ~0.5초 (CPU)
- 2단계는 수만 개 이상일 때 효과가 있음

## 9. 핵심 개념 요약

| 개념 | 한줄 설명 |
|------|----------|
| **RAG** | 외부 문서를 검색해서 LLM 답변에 근거를 제공하는 기법 |
| **Agentic RAG** | LLM이 검색 도구를 스스로 선택/조합/반복하는 자율형 RAG |
| **MCP** | Claude Desktop이 외부 도구를 호출하기 위한 표준 프로토콜 |
| **Embedding** | 텍스트를 숫자 벡터로 변환 (의미가 비슷하면 벡터도 비슷) |
| **Bi-Encoder** | 질문과 문서를 독립 인코딩 → 빠르지만 덜 정밀 |
| **Cross-Encoder** | 질문+문서를 함께 인코딩 → 느리지만 정밀 |
| **Reranking** | 1차 검색 후 Cross-Encoder로 순위 재조정 |
| **Overlap Chunking** | 청크 간 텍스트를 겹치게 해서 경계 정보 손실 방지 |
| **Parent-Child** | 검색은 작은 단위(Child)로, 반환은 큰 단위(Parent)로 |
| **Hybrid Search** | 벡터 검색 + 키워드 검색 결합 |
| **RRF** | 여러 검색 결과의 순위를 수학적으로 결합하는 방법 |
| **pgvector** | PostgreSQL에서 벡터 연산을 지원하는 확장 |
| **pg_trgm** | PostgreSQL에서 trigram 기반 유사 문자열 검색 지원 |
